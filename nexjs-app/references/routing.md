# Routing

File-system routing in the `app` directory. Folders define URL segments; files define UI and behavior for a segment.

## Special files

| File | Role |
|---|---|
| `page.tsx` | Renders at the segment's URL. Presence makes the segment public. |
| `layout.tsx` | Shared UI that wraps child segments. Preserves state across child navigations. |
| `template.tsx` | Like `layout` but remounts on navigation. Rare. |
| `loading.tsx` | Suspense fallback for the segment's `page`. |
| `error.tsx` | Error boundary (Client Component) for the segment subtree. |
| `not-found.tsx` | UI for `notFound()` calls inside the segment. |
| `global-error.tsx` | Root-level error boundary. Must include `<html>`/`<body>`. Root-only. |
| `route.ts` | HTTP endpoint handler (GET/POST/…). Cannot coexist with `page` at the same segment. |
| `default.tsx` | Fallback for parallel routes. |

## Nesting and URL shape

Folder name → URL segment. `app/blog/[slug]/page.tsx` → `/blog/:slug`.

| Pattern | Meaning |
|---|---|
| `[segment]` | Dynamic single-value segment |
| `[...segment]` | Catch-all |
| `[[...segment]]` | Optional catch-all |
| `(group)` | Route group — not in URL, used to share layouts or split into multiple root layouts |
| `_folder` | Private, not routable (colocated utils/components) |
| `@slot` | Named parallel slot rendered by parent layout |
| `(.)folder`, `(..)folder`, `(...)folder` | Intercepting routes (modals over siblings/parents/root) |

A route becomes public only when `page.tsx` or `route.ts` exists in the segment.

## Page props — `params` and `searchParams` are Promises

```tsx
// app/blog/[slug]/page.tsx
export default async function Page({
  params,
  searchParams,
}: PageProps<'/blog/[slug]'>) {
  const { slug } = await params
  const { sort } = await searchParams
  // ...
}
```

- `PageProps<'/blog/[slug]'>` is a global type, generated by `next dev`/`next build`/`next typegen`. No import.
- `LayoutProps<'/dashboard'>` similarly types layouts, including named slots as typed keys (e.g. `app/dashboard/@analytics/page.tsx` → `props.analytics`).
- Reading `searchParams` opts the page into dynamic rendering.

## Root layout

Required. Must contain `<html>` and `<body>`:

```tsx
export default function RootLayout({ children }: LayoutProps<'/'>) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  )
}
```

Multiple root layouts: remove the top-level `layout.tsx`, add one inside each route group (`app/(marketing)/layout.tsx`, `app/(shop)/layout.tsx`). Each must include `<html>`/`<body>`.

## Linking and navigation

- `<Link href="/blog">` — client-side nav, auto-prefetches on viewport entry (full route if static, shell + loading if dynamic with `loading.tsx`).
- `<a href>` — no prefetch, full reload.
- `prefetch={false}` on `<Link>` to opt out (useful in long lists).
- `useRouter()` from `next/navigation` for programmatic nav.
- `useLinkStatus()` exposes a `pending` boolean for in-flight transitions — use to render debounced spinners.

## Instant navigation with streaming

Dynamic routes feel slow without help. Add `loading.tsx` to enable partial prefetch and instant visual feedback:

```tsx
// app/blog/[slug]/loading.tsx
export default function Loading() {
  return <PostSkeleton />
}
```

For dynamic segments that *could* be prerendered, add `generateStaticParams`:

```tsx
export async function generateStaticParams() {
  const posts = await getPosts()
  return posts.map((p) => ({ slug: p.slug }))
}
```

## Native History API

`window.history.pushState` and `replaceState` integrate with the router — `usePathname` and `useSearchParams` sync automatically. Use for filters/sort state without navigation.

## Organizing the project

Next.js is unopinionated on project layout. Pick one and be consistent:

- Store non-route code *outside* `app` (root-level `components/`, `lib/`).
- Store it *inside* `app` (colocated under `app/components/`, `app/lib/`).
- Split by feature: shared in `app/`, feature-specific inside each route segment.
- Use `_components/`, `_lib/` private folders for per-segment colocation.

## Route groups — canonical uses

- Different layouts for different audiences: `app/(marketing)/layout.tsx` vs `app/(app)/layout.tsx`.
- Applying `loading.tsx` to only one page: move it into a new `(overview)/` group.
- Completely separate root layouts (different `<html>` structure): multiple root layouts via route groups.
